# xactflow-rtl-gen

A [XactFlow](https://github.com/IP-XACT/XactFlow) exporter plugin that generates the SystemVerilog
of an [IEEE 1685-2022](https://standards.ieee.org/ieee/1685/10307/) IP-XACT design: the module, its
instances and parameters, the bus and ad hoc wiring between them, and a package with its address map.

## Installation

```bash
pip install xactflow-rtl-gen
```

It adds the `rtl-gen` subcommand to `xactflow`. Requires Python >= 3.9, and XactFlow 0.3: the exporter uses a
private part of XactFlow's evaluator, so it is pinned below 0.4 until that is public.

For development, with the rest of the toolchain and the tests' tools:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
```

## Usage

From a design file:

```bash
xactflow rtl-gen soc.xml --lib ip/ --output rtl/
```

Chained straight from an importer. A design script's `ipxact.Design` holds only VLNV references, not
the ports and port maps the wiring comes from, so this form needs `lib`:

```bash
xactflow archidesc soc.py --then rtl-gen --then-option lib=ip/ --output rtl/
```

Both link the design and refuse it if linking reports errors. Regenerating replaces an earlier output,
but a file not generated by this tool is never overwritten: if one is in the way, nothing is written.

From Python:

```python
from xactflow import Library, link
from xactflow_rtl_gen import RtlExporter, generate_files

linked = link(design, Library.scan("ip"))
files = generate_files(linked, common=["clk_i", "rst_ni"])  # file names and their text
RtlExporter().export(linked, "rtl", common="clk_i,rst_ni")  # or written to rtl/
```

### What it writes

- `<module>.sv`: the design's module.
- `<module>_addr_map_pkg.sv`: its address map, if the design records address windows. Compile it first.
- One more `<module>.sv` for each hierarchical instance, at any depth.
- With the `filelist` option, a list of those files in an order that compiles.

### Options

- `common`: input port names to share across instances, for clocks and resets. Each one no connection
  drives connects to one port of the module with that name. Comma-separated, or a list from Python.
- `lib`: folders to scan for the library, when exporting an `ipxact.Design`. Comma-separated, or a list
  from Python.
- `top`: the VLNV of the hierarchical component to use, when more than one holds the design.
- `unconnected`: what happens to a port the design connects to nothing, in a module whose ports a
  hierarchical component defines: an instance's input, or an output of the module. `refuse`, the default,
  stops with an error. `open` leaves it as the design has it, open or undriven, with a comment that says
  so (D38).
- `filelist`: a file name, such as `soc.f`. The files of this run are listed in it, packages first and the
  design's module last, relative to the list: `verilator -F rtl/soc.f` (D39).

## What the output looks like

Every connected instance port gets its own net, `<instance>_<port>`, and each connection is an
`assign` from the driving net to the receiving one:

```systemverilog
    // m_to_s: m.bus <-> s.bus (test.org:bus:sbus_rtl:1.0)
    // s.bus address window: baseAddr 0x40000000, size 0x1000
    assign s_valid_ni = ~m_valid_o;  // VALID
    assign s_wdata_i  = m_wdata_o;  // WDATA
    assign m_rdata_i  = s_rdata_o[7:0];  // RDATA
    assign m_ready_i  = 1'h1;  // READY, abstraction default
    assign m_err_i    = 1'h0;  // ERR, tied off by s

    // IP-XACT VLNV: test.org:ip:master:1.0
    master_core m (
        // Interface: bus
        .clk_i    (clk_i),
        ...
```

That one shape covers part selects, inverted port maps, tie-offs and struct sub-ports. Two things add a
net of their own: a logical port mapped in slices, called `<connection>_<logical port>`, and an inout,
which has to share a net with what it connects to. A whole port wired to one of the module's own ports
connects directly, with no net in between, unless a part of it is taken elsewhere and the two number their
bits differently, or are structs of different types (D35). A net's name gets `_net` added if it would be a keyword, or already belongs to an
instance or a port.

## Where the module's ports come from

**With a hierarchical component in the library**, the component whose view holds the design defines the
module: its name, and exactly its ports. This is the standard's own way, and you can connect to those
ports with `externalPortReference` and `hierInterface`. An input no connection reaches is an error,
unless it is listed in `common`, because the component says what the ports are and floating an input is
a bug, and so is an output of the module that nothing drives. The option `unconnected=open` leaves both as
they are, for a design that means them to be. An instance's output nothing reads is left open.

If that view also names a component instantiation with module parameters, the module declares them, so
that code which instantiates it with `#(...)` still compiles. They do not configure it: each has the one
value the module is generated for, and the module has the compiler refuse any other (D36). A parameter is
declared with no type, so that nothing converts what it is given before it is compared; only a typedef named
with its package is kept (D41):

```systemverilog
module croc_soc #(
    parameter GpioCount = 32
) (
    ...
);

    if (GpioCount !== 32) begin : GpioCount_as_generated
        $error("croc_soc is generated for GpioCount = 32, and was given another value");
        initial $fatal(1, "croc_soc is generated for GpioCount = 32, and was given another value");
    end
```

`$error` stops a compiler as it elaborates the module. One that goes on past it stops when the simulation
starts, on the `$fatal` (D40).

**Without one**, the design is all there is. An `externalPortReference` declares a port. A port no
connection reaches becomes a top-level port, `<instance>_<port>`, or the shared `common` port, so
nothing floats silently. This is what you get from `archidesc` today, which cannot declare top-level
ports. Parts of a port with no hierarchical component are refused, and so is `hierInterface`, since only
the component can say which ports those are.

## How connections are decided

- **Module name of an instance:** the configured view's `moduleName`, else the first view with an
  instantiation, else the VLNV name. A component with no view takes its only component instantiation (D33).
- **A view's choices:** an instance uses the abstraction type, driver and type definitions of its view.
- **A design configuration:** the one given to `link()`, else the one the hierarchical component's view
  holds, at any depth.
- **A hierarchical instance:** its view holds a design, which gets its own module. Every value in a generated
  module is worked out, so an instance whose overrides change a parameter of its component gets a module of
  its own, `<module>_1`, `<module>_2`, ..., one for each set of values, however each instance writes them, with
  those values all the way down its design (D26). Its first line says which values it is for. If the module declares parameters (D36), the
  instance is given the values it is generated for.
- **A design's parameters:** a component's reference to the design it holds can give them values, worked out
  in the component, so a top component or a hierarchical instance sets its design's parameters this way. That
  works when the view names a design configuration as well, as Kactus2 writes it (D25). Its reference to the
  design configuration gives that one's parameters values the same way (D37).
- **Parameters:** every module parameter of the view is written, with its value in this design, because
  the HDL's own default can differ from the component's. The exception is one worked out only from the
  instance's other module parameters, as an imported HDL default such as `B = A + 8'd100` is: the HDL works
  that out itself, exactly, unless an override sets it. A value with no parameters in it is written as it
  stands, so `8'hA5` stays 8 bits, and so does a parameter's own value. One that uses other parameters is
  worked out, by the same evaluator as the port widths, so the two cannot disagree. It honours a parameter's
  declared type, and is written with the width the evaluator gives it, such as `8'd255`. What it can't work out, a
  string or something in a package, goes to the compiler with the numbers filled in. Overrides are applied
  here, since `link()` does not. A `runtime` parameter is left off the instance, and an override on one is
  refused.
- **Type parameters:** a module parameter whose `dataType` is `type`, as `xactflow-sv` imports SystemVerilog's
  `parameter type`, stands for a type. A port of that type is declared with the type its instance gives the
  parameter, such as `croc_pkg::sbr_obi_req_t`. Where that is `logic [W-1:0]` the port is a plain vector, and its
  width is checked like any other. A type parameter the HDL works out from its other parameters is left to
  it (D31).
- **Arrays of structs:** on a port that is a packed array of a struct, a part select picks elements. `[3:3]` is
  the element `[3]`: it connects to a struct of that type, and can have sub-ports, `[3].a.addr`, in a port map
  as in a design. A longer range connects whole to an array of as many. Every element of such an input has to
  be driven, whole or member by member (D32).
- **Expressions in the design:** part selects and tied values see the design's parameters, and then those
  of its hierarchical component, not the instance's. Values in a design configuration see its own first.
- **Constants on a net:** `'1` is all ones at that net's width. On a port or sub-port of a named type, such as
  an enum, a constant or an inverted value is cast to it, `mode_pkg::mode_e'(2)`. Where only the compiler knows
  the width, the module has it check that the constant fits, with `$bits` and `$error` at elaboration. slang,
  Verilator and Icarus 13 stop there. Icarus 12 skips such a line, and Verilator with `-Wno-fatal` only reports
  it.
- **A port map with no logical range:** on a wire port it takes logical bits [the port's width - 1:0], as Annex
  B.1.7 of the standard says, so an end narrower than the others gets the low bits, such as a 12-bit memory
  address on a 32-bit bus. A bit read that no end drives is refused, as the standard doesn't say what it gets.
  Where bits are picked by number, they have to lie within the abstraction's width for the port (SCR 6.19, D29).
- **A logical port with no driver on its bus:** the port map's `logicalTieOff`, else the abstraction's
  `defaultValue`, else its receivers stay unconnected. Tie-offs can each cover a logical range, next to
  bits a port drives. An abstraction's default reaches an inout only if nothing else on the bus connects to it.
- **An output a connected bus has no receiver for:** left open, `.port()`.
- **A port's own `defaultValue`:** applies only through an ad hoc `tiedValue="default"`, where it wins over
  the abstraction's default. Without one, an input nothing connects is treated like any other, whatever
  its default. This is 7.5.5 and Table C.2 of the standard, which `tests/test_scenarios.py` runs row by row.
- **Ad hoc `tiedValue`:** a constant, `open` for `.port()` on a whole port, or `default` for that default value. On a part
  select, `default` takes those bits of the default. A port's drivers can each cover a range of its bits.
- **Transactional and phantom ports:** left out, as an RTL view of the component does not have them.

## Address map

`archidesc`'s `connect_bus(..., base_addr=, size=)` records a window on the connection. The package holds
those windows as constants, and one rule table for each instance that decodes them:

```systemverilog
    localparam int unsigned DEC_NUM_RULES = 2;
    typedef addr_rule_t [DEC_NUM_RULES-1:0] DEC_ADDR_RULES_t;
    localparam DEC_ADDR_RULES_t DEC_ADDR_RULES = DEC_ADDR_RULES_t'({
        {32'd1, 32'h40001000, 32'h40003000},
        {32'd0, 32'h40000000, 32'h40001000}
    });
```

- A rule's `idx` is which interface of the decoder the window is behind, counted in the order the component
  declares them, among its `initiator` and `mirroredTarget` interfaces, whatever order the script connected
  them in. On a bus with several ends, the decoder is the end with one of those modes.
- A window reached through one of the module's own interfaces is listed under the module, with `idx`
  counting the hierarchical component's interfaces.
- Each window has `_BASE`, `_END` and `_SIZE` constants, named after the decoder and interface, and the target
  too when one interface reaches several windows.
- `addr_rule_t` has the same fields as PULP's `axi_pkg::xbar_rule_32_t`, and the same meaning: the end is
  exclusive, and an end of 0 means the end of the address space. A decoder that takes a `rule_t`, such as
  common_cells' `cc_addr_decode`, can take the table as it is.
- A decoder that declares module parameters called `ADDR_RULES` and `NUM_RULES` is given its table. Any
  other decoder has to be pointed at the package by a parameter override, such as
  `RULES="soc_addr_map_pkg::DEC_ADDR_RULES"`.
- `DEC_ADDR_PAIRS` holds the same windows as a flat vector of start and end pairs, rule 0 first, for a decoder
  that takes them that way.
- The address width comes from the logical port the abstraction marks with `isAddress`, and may use the
  abstraction's parameters. Each window has to fit its own bus; the package uses the widest. With no
  `isAddress` at all, it is 32 bits, or 64 if a window needs it.

## What it refuses

It raises `ValueError` rather than writing wrong RTL:

- link errors, including ad hoc references `link()` drops without a diagnostic;
- width mismatches, evaluated after parameter overrides, which neither `archidesc` nor the SCR checks
  catch today, including through an inout, and for a struct or sub-port when its sub-ports are declared (on a
  bus, ends mapped with no logical range may differ, D29);
- a whole port of a type only the compiler knows, such as an enum or a struct with no sub-ports listed,
  connected to anything but the same type or a constant, or tied to a default given in parts (one default for
  the whole port is cast and checked like any constant, D27);
- a constant or an inversion into an unpacked struct;
- an input driven twice or only partly, a logical port with two drivers, two different tie-offs, or a real
  driver and a tie-off on an end that would drive it, and logical bits read but never driven;
- an element of an array of structs that nothing drives, and a member of one, where the component lists the
  struct's members;
- a top-level output nothing drives;
- a constant that does not fit its port, positive or negative, which would silently lose bits (for a type only the
  compiler knows the width of, the compiler refuses it, through the check above);
- parameter overrides on a reference to a bus or an abstraction, or from a design configuration to its design,
  which nothing here would apply;
- a view that names a design and a design configuration for another design;
- a value on a reference to a design or a design configuration, or on a hierarchical instance, for a parameter
  that document or component does not have, and values for one design configuration when the design is linked
  with another;
- on a generated module: a type parameter, a parameter whose value cannot be compared, such as an assignment
  pattern, and one named like a port or an instance (D36);
- `tiedValue="open"` on a part of a port, as only a whole port can be left open;
- a name in a parameter's value that no parameter in scope explains, and a typedef whose name has no package,
  which a generated module could not see;
- address windows that overlap on one decoder or pass the end of their bus's address space, a window with no
  way to tell its decoder, and constants in the package whose names would come out the same;
- a parameter override that reaches no module parameter;
- a parameter or tied value that cannot be evaluated, or is outside its parameter's `minimum` or `maximum`;
- a design that contains itself, two different modules with the same name, and a generated module named like
  the module of an IP;
- a name that is not a valid SystemVerilog identifier or is a keyword, such as a component called
  `interconnect`, and an instance named like a port of the module;
- what would not stay where it is written: a parameter value that is not one value, a module parameter whose
  name is no identifier, and a type that is more than a type's name (D34);
- a view that names a component instantiation its component lacks, and a component with several component
  instantiations and no view to choose one.

## Limitations

- **Decoding is not generated.** The address map is data for a decoder that already exists. Nothing writes
  the crossbar itself.
- **Each error below is reported, not silently skipped.** Not supported yet: monitor interconnections,
  unpacked arrays (an instance's output that nothing connects is left open, D28), interface ports, indexed part selects, a part select on an inout, a subPort, a struct that is not a
  one-dimensional array, or a port with several dimensions, a part select running the other way from its port, a
  sub-port of an array of structs with no element picked, a constant into several elements of one, an abstraction's default next to tie-offs for some of its bits, an ascending logical range, an inverted inout, two inouts of the module on one net, logical slices on an inout of the module
  not declared from bit 0, abstractors, and type parameters on a generated module.
- **A generated module's parameters do not configure it.** It is generated for one value of each, and another
  value needs it generated again (D36). The module's own check of that stops a compiler, or else the simulation
  as it starts (D40).
- **A sub-port of a struct with no sub-ports listed cannot be width-checked.** `xactflow-sv` leaves them out.
  Nor is its type known, so a member that is an enum gets no cast, and slang and Verilator reject what drives it.
  Listing the sub-ports in the component fixes both (`docs/findings.md`, F2).
- **A width has to be something XactFlow's evaluator can work out.** `xactflow-sv` copies a port's dimensions
  from the module's header as they are written. A call of a package's function there, or a member of a
  struct-valued parameter, such as `cf_math_pkg::idx_width(N)` or `Cfg.AddrWidth`, is refused: the component has
  to give the number, or the function's body. A type the module gets through `import pkg::*` needs its package
  in the component as well.
- **Anything using a parameter goes through XactFlow's evaluator,** which simplifies some of SystemVerilog's
  rules on sign and width. A value written without parameters is the compiler's to work out, so if it also
  sizes a port, in a way the two read differently, they can disagree. Tools warn about the port width.
- **Transforms are not applied.** `<xactflow:transforms>` shows as a comment on the instance.
- **`common` is this plugin's own option, not IP-XACT.** It exists because `archidesc` has no way to fan
  one input out to several instances. A design written in XML can use `externalPortReference` instead.
- **`archidesc` cannot write a `tiedValue`,** so a design script cannot ask for a port's default value.
- **Two behaviours rest on a reading the standard does not settle.** The 2022 text has no rule or example
  for either. A `logicalTieOff` drives the receivers on the other side of the bus: 6.7.3.2 makes it the
  connection for that logical port in place of a physical port, and 6.5.5.2 connects interfaces by logical
  bit, but neither says the constant crosses over. `invert` applies on a hierarchical component's own port
  map: 6.7.3.2 defines it for connections to the physical port and makes no exception, but doesn't name
  this case either.

## Compared with Kactus2

Kactus2 has the established open-source generator for this, and several ideas here come from studying it:
ports from the hierarchical component, a net per logical port for slices, and the list of situations a
generator has to handle. No code comes from it: it is GPL-2, written in C++.

Both were run on the same designs, 43 connection scenarios and the XactFlow author's example SoC. On 33 of
the 44 both pass the same simulation, or compile where there is none, and connect every bit the same way.
In the other 11 this tool passes and Kactus2 does not. The expected values are this project's own, so these
are differences to weigh, not proof:

- `invert` on a hierarchical component's own port map (1 design): Kactus2 ignores it. The standard makes no
  exception for this case, but doesn't name it.
- `logicalTieOff` (2 designs): Kactus2's generator does not read it. The standard doesn't settle whether it
  crosses the bus.
- Default values (3 designs): where `tiedValue="default"` or no default should apply, Kactus2 drives the input
  twice. It also ties an unconnected input to its own default, which 7.5.5 and Table C.2 of the standard
  rule out. This tool did the same, until checking the standard's text.
- `tiedValue="default"` on a part select (1 design): Kactus2 takes the low bits of the default.
- An inout tied to a constant (1 design): Kactus2 leaves it open.
- A port typed `int` (1 design): Kactus2 makes a 1-bit net.
- A design's parameter in a part select (1 design): Kactus2's output does not compile.
- The scenario using `common` (1 design), which Kactus2 does not have.

Kactus2 also generates Verilog that does not compile if a top-level port is called `<instance>_<port>`.

## Tried on real designs

Besides its own tests, the exporter is run on whole SoCs, each chosen for a kind of input the others lack (D24
in `docs/decisions.md`). The scripts for these are kept outside this repository.

- **[Didactic SoC](https://github.com/Edu4Chip/Didactic-SoC)** (Edu4Chip): an IEEE 1685-2022 library made in
  Kactus2, with three levels of hierarchy and design configurations. All eight modules generate, and every bit
  of every instance is driven as in the Verilog Kactus2 generated, but for eight bits of one port that the RTL
  makes narrower than the IP-XACT. Elaborated with the RTL in Didactic's repository, the generated modules fit
  it, once four module parameters the RTL does not have are taken out of one component.
- **[Croc](https://github.com/pulp-platform/croc)** (PULP): a hand-written SoC of IPs with type parameters and
  struct ports. Its `croc_soc` and `croc_domain` were described in IP-XACT, from components `xactflow-sv`
  imported, and generated. With the generated modules in place of the hand-written ones, Croc's testbench
  elaborates in slang and lints in Verilator with the same messages, and each of the 3769 port bits traced has
  the same driver, and each of the 110 instance parameters the same value. Croc's firmware, nine programs run
  in Verilator, passes on both and prints the same lines at the same simulation times. The generated `croc_soc`
  declares the parameter Croc's testbench gives it, so the testbench is used as it is.

## Development

```bash
.venv/bin/pytest
```

- `tests/test_scenarios.py` runs each connection scenario through slang, Verilator and an Icarus Verilog
  simulation. Then it breaks every generated `assign` in turn and requires the simulation to notice.
- `tests/test_address_map.py` decodes real addresses through a generated module.
- `tests/test_exporter.py` and `tests/test_top_component.py` hold the rules around these, and every refusal.
- `tests/test_adversarial.py` holds designs written to get wrong RTL past the exporter, and that once did.
- `tests/test_type_parameters.py` holds type parameters and arrays of structs as PULP's IPs have them, the last
  of them imported by `xactflow-sv` itself.
- `tests/test_module_parameters.py` holds the parameters of a generated module, and that each tool refuses an
  instance that gives one another value.

Verilator and Icarus Verilog are skipped when not installed; slang always runs. CI installs both from Ubuntu's
packages.
